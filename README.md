## 🌟 1. Опис функціоналу програми
Проєкт являє собою повноцінний інтерактивний застосунок для гри в шахи між двома гравцями. У програмі реалізовано:
- **Повний шаховий рушій:** контроль за дотриманням правил шахів, включно зі специфічними ходами (рокіровка, взяття на проході, перетворення пішака).
- **Менеджер часу (Chess Clock):** окремі таймери з лімітом часу для кожного гравця, що автоматично перемикаються після ходу.
- **Підрахунок рахунку серії ігор:** динамічне збереження результатів матчів між перезавантаженнями сторінки за допомогою `LocalStorage` (рахунок не скидається на 0-0 при оновленні вкладки).
- **Збереження стану (State Persistence):** якщо користувач випадково закриє вкладку, поточна партія автоматично відновиться у тому ж стані.
- **Аналітика та статистика матчу:** відстеження найактивнішої фігури на дошці, середнього часу роздумів Білих/Чорних та кількості оголошених шахів.
- **Кастомізація інтерфейсу:** вибір візуальних стилей дошки (тем оформлення).
- **Експорт ходів:** можливість вивантаження історії поточної партії у текстовий файл `.txt` для подальшого аналізу.
- **Аудіосистема:** звуковий супровід основних подій (хід, взяття фігури, шах, кінець гри) з можливістю повного вимкнення звуку (`Mute`).

## 3. Programming Principles (Принципи програмування)

Під час написання коду було суворо дотримано ключових стандартів Clean Code та SOLID для забезпечення чистоти архітектури:

1. **Single Responsibility Principle (SRP / Принцип єдиної відповідальності):**
   Кожен клас вирішує лише одну конкретну задачу. Наприклад, `SoundManager` керує виключно аудіоефектами, `ScoreManager` — веденням рахунку серії ігор, а `MoveHistory` — збереженням історії ходів.
   
2. **Don't Repeat Yourself (DRY):**
   Уся повторювана логіка винесена в окремі методи та сервіси. Наприклад, виклик тостів-сповіщень реалізовано через єдиний об'єкт `NotificationManager`, що усуває дублювання коду в UI-шарі.
   
3. **Keep It Simple, Stupid (KISS):**
   Внутрішня структура шахової дошки представлена у вигляді простої та зрозумілої двовимірної матриці клітинок (`cells[y][x]`). Це спрощує розуміння коду іншими розробниками та полегшує дебаг алгоритмів.
   
4. **YAGNI (You Aren't Gonna Need It):**
   Проєкт містить виключно той функціонал, який був закладений у ТЗ та вимоги до шахової гри. Немає жодних надлишкових абстракцій "на майбутнє", що дозволило зберегти лаконічність структури.
   
5. **Encapsulation (Інкапсуляція):**
   Важливі внутрішні дані класів (наприклад, масив фігур, стан таймерів, час початку ходу `moveStartTime`) захищені модифікатором `private`. Зміна стану об'єктів відбувається контрольовано — виключно через публічні методи-сетери.

## 4. Design Patterns (Патерни проєктування)

Для гнучкої побудови архітектури та вирішення задач генерації й поведінки об'єктів було впроваджено 3 архітектурні патерни:

### Патерн 1: Strategy (Стратегія) — Патерн поведінки
- **Де використано:** У базовому абстрактному класі фігури `Piece` та його конкретних спадкоємцях: `Pawn`, `King`, `Knight`, `Rook`, `Bishop`, `Queen`.
- **Навіщо:** Кожна фігура має абсолютно унікальний алгоритм перевірки можливості зробити хід. Замість гігантської конструкції `if-else` чи `switch` всередині головного рушія гри, логіка валідації ходу інкапсульована в метод `canMove(...)` кожного окремого класу фігури. Рушій гри `GameEngine` викликає цей метод поліморфно, не заглиблюючись у деталі реалізації ходу конкретної фігури. Це дозволяє легко додавати нові нестандартні фігури без зміни коду рушія.

### Патерн 2: Factory Method (Фабричний метод) — Породжувальний патерн
- **Де використано:** У методі відновлення збереженої партії `loadSavedGameIfPresent()` та при перетворенні пішака `handlePawnPromotion()` у файлі `src/core/GameEngine.ts`.
- **Навіщо:** При завантаженні матриці гри з файлу збереження (`LocalStorage`) ми отримуємо лише рядкові назви типів фігур (наприклад, `"King"`, `"Queen"`). Програма використовує умовну фабрику (`switch-case` конструкцію), яка на основі текстового типу динамічно породжує (інстанціює) правильні об'єкти класів (`new King()`, `new Queen()` тощо). Це ізолює процес створення об'єктів від їх використання.

### Патерн 3: Singleton (Одинак)
- **Де використано:** `SoundManager.getInstance()`, `ThemeManager.getInstance()`, `NotificationManager.getInstance()`.
- **Навіщо:** Гарантує, що у системі буде існувати лише один єдиний глобальний екземпляр класу для керування аудіо-ресурсами, стилями дошки чи сповіщеннями. Це запобігає конфліктам у виведенні UI, дублюванню аудіотреків та оптимізує використання оперативної пам'яті комп'ютера.

## 5. Refactoring Techniques (Техніки рефакторингу)

У процесі розробки та очищення коду від "запахів коду" (Code Smells) було виконано рефакторинг із застосуванням таких технік:

1. **Extract Method (Виділення методу):**
   Початковий величезний метод життєвого циклу ходу (`executeMoveLifecycle`) містив занадто багато обов'язків. Його було розбито на серію дрібних і читаваних приватних під-методів: `handleCastling`, `handlePawnPromotion`, `handleEnPassant`.
   
2. **Rename Method / Variable (Перейменування методів та змінних):**
   Усі ідентифікатори перейменовано відповідно до специфікації Clean Code та суті бізнес-логіки. Абстрактні змінні замінено на самодокументовані назви, такі як `wouldLeaveKingInCheck`, `terminateGame`, `isCheckmate`.
   
3. **Move Method / Class (Переміщення методу):**
   Логіку відстеження кліків миші по клітинках дошки та візуального рендерингу було повністю вилучено з ядра гри `GameEngine` та перенесено в окремі UI-класи відображення — `BoardView` та `ScoreboardView`. Це дозволило розділити бізнес-логіку та шар представлення (Separation of Concerns).
   
4. **Replace Temp with Query (Заміна тимчасової змінної запитом):**
   Замість того, щоб зберігати проміжні булеві прапорці стану шаху чи мату в локальних змінних функцій, використовуються динамічні виклики чистих методів-запитів, таких як `this.isCheck(color)`.
   
5. **Decompose Conditional (Декомпозиція умовних виразів):**
   Складні заплутані перевірки умов завершення партії, які виконувалися після кожного переміщення фігури, було декомпоновано та винесено в окремий акуратний метод `handlePostMoveChecks()`.
